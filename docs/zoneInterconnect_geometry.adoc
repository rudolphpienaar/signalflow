== Status

This document defines the overlap-oriented geometry algebra for adjacent routing zones. It replaces the earlier seam/interconnect doctrine as the target model for world-scale geometry. The normative concepts here are local zone mutation, adjacency constraint satisfaction, and monotone world propagation away from the fixed north-west anchor.

The target implementation is not a seam solver. It is a board-owned zone geometry system with an inspect/API facade that can express, apply, and reason about geometric changes naturally.

Current refinement:

- the next semantic owner beneath this doctrine is intended to be symbolic
  topology
- local mutation and overlap doctrine should increasingly attach to symbolic
  regions and family relations rather than only to inferred concrete frames

Read with:

- `docs/geometry_symbolic_topology.adoc`
- `docs/board.adoc`

== Motivation

Zone-local routing is now the solved problem. Each zone already has enough internal structure to solve its own intra substrate. The unresolved problem at world scale is not local routing but geometric coordination between adjacent zones.

The old seam model treated the shared face between zones as a separate routed body. That ontology is now considered wrong. The intended model is overlap: two adjacent zones share a terminal-facing band, and their local geometries must be harmonized so that the shared band is consistent for both.

That leads to two architectural requirements:

. a local mutation language for authoritative zone geometry
. a world propagation/resolution machine that preserves adjacency constraints while moving only east and south

== Core Model

=== Zone-Local Authority

Each zone owns one authoritative local substrate. The zone is not decomposed into an `intra/west/east/north/south` kernel cross as a first-class runtime ontology. Those slices may still exist temporarily as compatibility projections, but the true geometry owner is the zone itself.

Each zone geometry contains region families such as:

* chip-terminal bands
* fan-in/out bands
* intra longitude bands
* intra latitude bands
* extra longitude bands
* extra latitude bands
* transition/transfer bands

All mutations operate on these board-owned region families.

=== Overlap Instead Of Seam

For two horizontally adjacent WTE zones stem:[A] and stem:[B]:

* the east-facing terminal-side geometry of stem:[A] and the west-facing terminal-side geometry of stem:[B] must be harmonized
* the extra routing rings of the two zones must not geometrically collide
* any necessary growth shifts geometry away from the fixed north-west world anchor

There is no separate seam body. Adjacency is expressed as a constraint between neighboring zone geometries.

== API Direction

=== Inspect Surface

The inspect/API layer should expose intent in zone terms rather than raw frame surgery. Methods should follow the repo's RPN-flavored naming style and be attached to geometry-owning objects.

Examples:

[source,python]
----
zone.geometry.extentMax_align(regionFamily, neighborZone)
zone.geometry.extent_set(regionFamily, extent)
zone.geometry.padding_add(regionFamily, padding)
zone.geometry.shift_apply(regionFamily, deltaCols, deltaRows)
zone.geometry.overlapWithNeighbor_align(face, neighborZone)
----

The key point is that the inspect layer exposes operations that are easy to reason about. It should not require the caller to manually mutate individual `horizontalStart` or `verticalStart` fields.

=== Mutation Objects

The implementation should model changes declaratively before applying them.

[source,python]
----
@dataclass(frozen=True)
class ZoneGeometryMutation:
    regionFamily: RegionFamily
    kind: ZoneGeometryMutationKind
    magnitude: int


@dataclass(frozen=True)
class ZoneAdjacencyConstraint:
    sourceZoneId: ZoneId
    destinationZoneId: ZoneId
    face: ZoneFace
    kind: ZoneAdjacencyConstraintKind
----

The important distinction is:

* mutation: local requested change
* constraint: relation between adjacent zones
* propagation: world-level consequence of satisfying those constraints

== Extent Harmonization

=== Terminal-Face Max Alignment

For two adjacent zones stem:[A] and stem:[B], let:

[stem]
+++
\begin{aligned}
T^{E}_{A} &= \text{east terminal-face extent of zone } A \\
T^{W}_{B} &= \text{west terminal-face extent of zone } B
\end{aligned}
+++

The shared overlap extent is:

[stem]
+++
T^{\max}_{A,B} = \max(T^{E}_{A}, T^{W}_{B})
+++

The harmonization rule is:

[stem]
+++
\begin{aligned}
\widehat{T}^{E}_{A} &= T^{\max}_{A,B} \\
\widehat{T}^{W}_{B} &= T^{\max}_{A,B}
\end{aligned}
+++

That is the semantic meaning of a call such as:

[source,python]
----
zoneA.geometry.extentMax_align(RegionFamily.EAST_TERMINAL, zoneB)
zoneB.geometry.extentMax_align(RegionFamily.WEST_TERMINAL, zoneA)
----

If one side is already maximal, only the smaller side changes. The larger side is stable.

=== Local Reshape Delta

For the non-max side, the required additional extent is:

[stem]
+++
\Delta T_{B}^{W} = T^{\max}_{A,B} - T^{W}_{B}
+++

and similarly for stem:[A] if it is the smaller side.

The local reshape operation is then:

[stem]
+++
\widehat{G}_{B} = \operatorname{reshape}(G_{B}, \text{west-terminal}, \Delta T_{B}^{W})
+++

where stem:[G_{B}] is the full zone geometry of zone stem:[B].

== Extra-Ring Padding

After terminal harmonization, adjacent extra-ring families may still geometrically collide. Let:

[stem]
+++
\begin{aligned}
X^{E}_{A} &= \text{east extra-ring span of zone } A \\
X^{W}_{B} &= \text{west extra-ring span of zone } B
\end{aligned}
+++

The minimum separation budget for the two sides is:

[stem]
+++
P^{\min}_{A,B} = X^{E}_{A} + X^{W}_{B}
+++

The inspect/API surface should express this as a padding mutation:

[source,python]
----
zoneB.geometry.padding_add(RegionFamily.WEST_EXTRA_LONGITUDE, padding)
----

with the semantic constraint:

[stem]
+++
\widehat{P}_{A,B} \ge P^{\min}_{A,B}
+++

The important design point is that `padding_add(...)` is not a world solver. It is a local request that creates downstream displacement inside the zone.

== Directed Local Shift

Given invariant world anchor stem:[(1,1)], every geometric consequence of growth must move only:

* eastward, stem:[+\Delta x]
* southward, stem:[+\Delta y]

There is no legal negative displacement.

[stem]
+++
\Delta x \ge 0,\qquad \Delta y \ge 0
+++

For a WTE zone, a local perturbation of any west/east-facing family can induce:

* routing-sense motion: eastward
* orthogonal motion: southward

if vertical rebalancing is needed to preserve internal spacing or overlap alignment.

=== Local Downstream Shift Rule

For a region family stem:[R] with anchor start stem:[s(R)], and a perturbation magnitude stem:[\delta], every downstream family stem:[Q] on that axis satisfies:

[stem]
+++
s'(Q) =
\begin{cases}
s(Q) + \delta, & s(Q) \ge s(R) \\
s(Q), & s(Q) < s(R)
\end{cases}
+++

This is the abstract meaning of:

[source,python]
----
zone.geometry.shift_apply(regionFamily, deltaCols, deltaRows)
----

The implementation should eventually operate on typed region families rather than name strings.

== World Propagation

=== Why A Resolver Is Required

Local mutation alone is insufficient. If zone stem:[B] grows on its west face:

* downstream geometry inside stem:[B] moves east and/or south
* the fixed overlap with zone stem:[A] may become inconsistent
* zone stem:[A] may have to grow or shift to preserve the shared overlap band
* those changes may then affect the next neighbor

So the system needs a world propagation machine.

=== World Resolver

The intended resolver is something like:

[source,python]
----
class WorldGeometryResolver:

    @staticmethod
    def mutations_apply(
        world: WorldGeometryState,
        mutations: tuple[ZoneGeometryMutation, ...],
    ) -> WorldGeometryState:
        ...

    @staticmethod
    def constraints_satisfy(
        world: WorldGeometryState,
        constraints: tuple[ZoneAdjacencyConstraint, ...],
    ) -> WorldGeometryState:
        ...

    @staticmethod
    def propagate_run(world: WorldGeometryState) -> WorldGeometryState:
        ...
----

Its job is to:

. apply local zone mutations
. enforce adjacency constraints
. accumulate world displacement
. preserve monotonicity away from stem:[(1,1)]

=== Monotone Propagation

Let the absolute world displacement of zone stem:[Z_{i,j}] be:

[stem]
+++
\Delta(Z_{i,j}) = (\Delta x_{i,j}, \Delta y_{i,j})
+++

The monotonicity invariant is:

[stem]
+++
\Delta x_{i,j} \ge 0,\qquad \Delta y_{i,j} \ge 0
+++

and for east/south neighbors:

[stem]
+++
\begin{aligned}
\Delta x_{i,j+1} &\ge \Delta x_{i,j} \\
\Delta y_{i+1,j} &\ge \Delta y_{i,j}
\end{aligned}
+++

That does not yet define the full propagation law, but it does define the non-negotiable directional invariant.

== Prefix-Sum Case

If all overlap and padding budgets are pure policy and do not depend on solved-wire demand, then the world propagation may admit a one-pass cumulative solution.

For example, with horizontal adjacency budgets stem:[H_{i,j}] and vertical adjacency budgets stem:[V_{i,j}], one possible world displacement law is:

[stem]
+++
\begin{aligned}
\Delta x(i,j) &= \sum_{k=1}^{j-1} H_{i,k} \\
\Delta y(i,j) &= \sum_{k=1}^{i-1} V_{k,j}
\end{aligned}
+++

This is the overlap-model analogue of the earlier seam prefix-sum idea.

Whether the budget should be:

* sum
* max
* or a richer shared-band function

is still an open design question. The important architectural point is that the world solver consumes local budgets; it does not directly mutate raw zone frames itself.

== Future Demand-Driven Case

If overlap budgets become demand-driven, then the system may require iteration.

[stem]
+++
\text{zone specs}
\rightarrow \text{local mutations}
\rightarrow \text{adjacency budgets}
\rightarrow \text{world propagation}
\rightarrow \text{updated zone specs}
\rightarrow \cdots
+++

That is a future concern. The immediate objective is to build:

* a board-owned zone geometry mutation language
* typed adjacency constraints
* a monotone world propagation machine

== Implementation Direction

The next implementation phases implied by this doctrine are:

. materialize a board-owned `ZoneGeometry` object that can express typed region families and local mutation intents
. expose that naturally through the inspect/API surface using RPN-style names like `extent_set`, `padding_add`, and `extentMax_align`
. build a world resolver that propagates only south/east
. keep current seam/interconnect solved routes only as temporary compatibility continuity until overlap-based cross-zone routing exists

== Symbolic Anchor Displacement Algebra

The doctrine above defines the physics of zone mutation and world propagation. This section defines the implemented rule algebra that makes displacement accessible through named symbolic handles rather than raw frame surgery.

The implementation lives in `src/signalflow/board/geometry/georules.py`.

=== Primitive Operations

==== Axis Resolution

Every anchor token has an axis.  E- and W-prefix anchors are horizontal; N- and S-prefix anchors are vertical.  A scalar displacement stem:[\delta] on an anchor stem:[A] resolves to a two-dimensional displacement vector:

[stem]
+++
(\Delta x, \Delta y) =
\begin{cases}
(\delta, 0) & \text{if } A \in \{\text{E*}, \text{W*}\} \\
(0, \delta) & \text{if } A \in \{\text{N*}, \text{S*}\}
\end{cases}
+++

This is the only place axis direction enters the algebra.  All downstream operations receive stem:[(\Delta x, \Delta y)] and are axis-agnostic.

==== Frame STRETCH

A STRETCH applies a signed delta to one named face of a zone frame stem:[F = (x_0, y_0, w, h)]:

[stem]
+++
\operatorname{stretch}(F, \text{face}, \delta) =
\begin{cases}
(x_0,\; y_0,\; w + \delta,\; h) & \text{east} \\[4pt]
(x_0 + \delta,\; y_0,\; w - \delta,\; h) & \text{west} \\[4pt]
(x_0,\; y_0,\; w,\; h + \delta) & \text{south} \\[4pt]
(x_0,\; y_0 + \delta,\; w,\; h - \delta) & \text{north}
\end{cases}
+++

A positive east/south delta grows the zone outward on that face. A positive west/north delta — typically stem:[\delta < 0] in practice — shrinks the zone from that face, consuming interior space.

==== Frame TRANSLATE

A TRANSLATE shifts a zone frame rigidly by stem:[(\Delta x, \Delta y)]:

[stem]
+++
\operatorname{translate}(F, \Delta x, \Delta y) =
(x_0 + \Delta x,\; y_0 + \Delta y,\; w,\; h)
+++

Span is unchanged.  The entire frame moves as a unit.

=== Zone Collection

A `ZoneRegionCollect` descriptor names an anchor zone and a cardinal direction. When dispatched, the engine calls `zonesCollect_get` to produce the set of all first-class zones strictly beyond the anchor in that direction.

For a horizontal axis (EAST or WEST), let stem:[c_A = \text{horizontalStart}(A)]:

[stem]
+++
\mathcal{C}(A, \text{EAST}) = \bigl\{ Z_j \in \mathcal{Z} \mid \text{horizontalStart}(Z_j) > c_A \bigr\}
+++

[stem]
+++
\mathcal{C}(A, \text{WEST}) = \bigl\{ Z_j \in \mathcal{Z} \mid \text{horizontalStart}(Z_j) < c_A \bigr\}
+++

For a vertical axis (SOUTH or NORTH), substitute stem:[\text{verticalStart}] for stem:[\text{horizontalStart}].

The anchor zone itself is excluded.  Only first-class zones in stem:[\mathcal{Z} = \text{geometryZonesById}] participate; routing sub-regions are not collected.

Boundary frames follow the collection when their centre coordinate falls in the same directional half.  For EAST:

[stem]
+++
\text{include boundary } B \iff \frac{x_0(B) + w(B)}{2} > c_A
+++

=== The Global Sentinel: sfN.Z

`sfN.Z` is a rule-bank sentinel meaning "apply to every zone in the geometry." It is not a real zone; it resolves to stem:[\mathcal{Z}] in full.

Its primary use is the floor guard pattern for anchors that displace toward the world origin (west or north).  If a west-facing anchor contracts by stem:[m > 0] columns, a naive translate would push zones toward or past column zero.  The floor guard fires first:

[stem]
+++
\operatorname{translate}(Z_j, -\delta, 0) \quad \forall\, Z_j \in \mathcal{Z}
+++

shifting the entire routing core east by stem:[\delta] before the named anchor is translated back west by stem:[\delta].  The net absolute displacement of the anchor is zero; the routing core opens the required space behind it.

=== Rule Entry and Factor

Each entry in `RULES[anchor][op]` is a tuple stem:[(\text{target}, \text{face}, \text{effect}, k)] where stem:[k \in \{-1, +1\}] is the factor.  The applied delta for the entry is:

[stem]
+++
\delta_{\text{applied}} = k \cdot \delta
+++

For the floor guard entry, stem:[k = -1], so a positive anchor displacement produces a negative translation on stem:[\mathcal{Z}] — moving all zones toward the origin first.  For all other entries, stem:[k = +1].

=== Rule Ordering Constraint

Rule entries are applied sequentially in list order.  The ordering is load-bearing for any rule that uses the sfN.Z floor guard.  The invariant is:

_The stem:[\mathcal{Z}] translate must precede any entry that moves the named anchor, because the anchor's subsequent translate depends on the zones already being at their guarded positions._

Reversing the order causes the anchor to move first into a collision position and the subsequent global shift to compound rather than cancel the displacement.

=== Concrete Rules

==== Et += n (east chip terminal expansion)

[stem]
+++
\begin{aligned}
\mathcal{C}(\text{Efi}, \text{EAST}) &\xrightarrow{+n,\; 0} \text{TRANSLATE} \\
\text{Efi.east face} &\xrightarrow{+n} \text{STRETCH} \\
\text{Ne.east face} &\xrightarrow{+n} \text{STRETCH} \\
\text{Se.east face} &\xrightarrow{+n} \text{STRETCH}
\end{aligned}
+++

No floor guard needed: Et moves east, away from the world origin.  Efi widens to stay abutting the displaced terminal wall.  The Ne/Se corner zones widen eastward to cover the expanded perimeter.

==== We -= m (west extra ring contraction, stem:[\delta = m > 0])

[stem]
+++
\begin{aligned}
\mathcal{Z} &\xrightarrow{-m,\; 0} \text{TRANSLATE} \quad \text{(floor guard, factor } {-1}\text{)} \\
\text{We} &\xrightarrow{+m,\; 0} \text{TRANSLATE} \quad \text{(net zero on We)} \\
\text{Ne.west face} &\xrightarrow{-m} \text{STRETCH} \\
\text{Se.west face} &\xrightarrow{-m} \text{STRETCH}
\end{aligned}
+++

The routing core shifts east by stem:[m]; We holds its absolute position; the Ne/Se west corners shrink to match.

==== Ne -= n (north extra ring contraction, stem:[\delta = n > 0])

[stem]
+++
\begin{aligned}
\mathcal{Z} &\xrightarrow{0,\; -n} \text{TRANSLATE} \quad \text{(floor guard, factor } {-1}\text{)} \\
\text{Ne, Nt, Nfi, Nfe} &\xrightarrow{0,\; +n} \text{TRANSLATE} \quad \text{(hold position)} \\
\text{We.north face} &\xrightarrow{-n} \text{STRETCH} \\
\text{Wi.north face} &\xrightarrow{-n} \text{STRETCH} \\
\text{Ei.north face} &\xrightarrow{-n} \text{STRETCH} \\
\text{Ee.north face} &\xrightarrow{-n} \text{STRETCH}
\end{aligned}
+++

The routing core shifts south by stem:[n]; the north perimeter cluster holds; all four long channels have their north face contracted to match.

==== Se += n (south extra ring expansion)

[stem]
+++
\begin{aligned}
\text{Se, St, Sfi, Sfe} &\xrightarrow{0,\; +n} \text{TRANSLATE} \\
\text{We.south face} &\xrightarrow{+n} \text{STRETCH} \\
\text{Wi.south face} &\xrightarrow{+n} \text{STRETCH} \\
\text{Ei.south face} &\xrightarrow{+n} \text{STRETCH} \\
\text{Ee.south face} &\xrightarrow{+n} \text{STRETCH}
\end{aligned}
+++

No floor guard needed: Se moves south, away from the world origin.

=== Relaxation Zone-Boundary Constraint

After rules are applied and geometry is displaced, the routing-frame relaxation in `regionFramesRelaxed_build` must respect zone boundaries.  Let:

[stem]
+++
\phi_{\text{Ni}} = \text{verticalStart}(\text{Ni zone})
+++

[stem]
+++
\phi_{\text{Si}} = \text{verticalEnd}(\text{Si zone})
+++

The relaxation loop may propose upward shifts to the Ni routing frame (reducing its stem:[\text{verticalStart}]) to relieve wire pressure.  The constraint is:

[stem]
+++
\text{verticalStart}'(\text{Ni routing frame}) \ge \phi_{\text{Ni}}
+++

Symmetrically for Si:

[stem]
+++
\text{verticalEnd}'(\text{Si routing frame}) \le \phi_{\text{Si}}
+++

Any proposed shift that violates either constraint terminates the relaxation loop immediately.  stem:[\phi_{\text{Ni}}] and stem:[\phi_{\text{Si}}] are recorded from `regionFramesByName` before the loop begins and are not updated during iteration.

== Summary

The earlier seam/interconnect doctrine was valuable as a first description of adjacent-zone collision. But the target architecture is now different.

The correct model is:

* authoritative zone-local geometry
* overlap-driven adjacency constraints
* local mutation primitives
* monotone world propagation

The symbolic anchor displacement algebra described above is the implemented interface to those local mutation primitives.  Each anchor token encodes the full cascade of geometric consequences as an explicit, inspectable rule bank.  The algebra is axis-agnostic after resolution, monotone in the direction of displacement, and order-dependent wherever floor guards are required.

This is the substrate required before full clean-room world routing can replace the remaining compatibility seam machinery.
