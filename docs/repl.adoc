== Overview

The new-engine REPL is the primary inspection surface for SignalFlow.

It is not a separate query language. It is a curated Python console over the
actual typed engine state:

- validated `CircuitDocument`
- placed `RoutingZoneGrid`
- chip placements
- route obligations
- solved route layers
- world composition

The intended use is:

- load one YAML document
- inspect the placed and solved world directly
- ask concrete geometry questions in the REPL
- refine the engine and docs from those observations

Run it with:

[source,bash]
----
signalflow --engine new --repl path/to/document.yaml
----

Example:

[source,bash]
----
signalflow --engine new --repl examples/branch-converging.yaml
----

== Visual Surfaces

The REPL currently exposes three different kinds of visual inspection. They are
related, but they are not the same thing.

=== 1. Schematic Zone Draw

This is the abstract zone drawing:

[source,python]
----
z = zones.routingZone_get(1, 1)
z.routingZone_draw()
----

Use this when you want the zone as a debug schematic rather than a literal
world-canvas crop.

=== 2. Kernel Crossbar Map

To see how the 5 kernels are spatially organized within a zone:

[source,python]
----
z = zones.routingZone_get(1, 1)
z.routingZoneCrossbar_draw()
----

=== 3. Pixel Region Fill (Per Kernel)

This is the kernel-owned region map:

[source,python]
----
z = zones.routingZone_get(1, 1)
ki = z.routingKernel_get('intra')
ki.kernelAreas_get().draw("pixel")
----

This answers questions like:

- where does `east/inter_routing_fan_in_out` begin
- how wide is `west/inter_routing_longitude`
- which columns belong to the chip terminal region

=== 4. Zone As World Draws It

This is the authoritative per-zone crop from the composed world canvas:

[source,python]
----
z = zones.routingZone_get(1, 1)
z.routingZoneWorldCanvas_print()
----

This is the right surface when the question is:

- what does this zone actually look like inside `world.canvas_print()`
- where do chip bodies and route glyphs land in the final composition

== Life Hacks

=== Pixel Render A Kernel's Owned Regions

When you want to verify spans and ownership bands:

[source,python]
----
z = zones.routingZone_get(1, 1)
kw = z.routingKernel_get('west')
kw.kernelAreas_get().draw("pixel")
----

Useful follow-ups:

[source,python]
----
areas = kw.kernelAreas_get()
areas.names_print()
area = z.routingZoneArea_get("east/inter_routing_fan_in_out")
area.frame
area.geometry
----

=== Draw A Kernel's Specific Wiring

If you want to see only the routes solved by a specific kernel:

[source,python]
----
z = zones.routingZone_get(2, 1)
kw = z.routingKernel_get('west')
kw.kernel_routesDraw()
----

=== Inspect An Interconnect Directly

Interconnects now have the same practical visual modes:

[source,python]
----
ic = interconnects.routingZoneInterconnect_get(1, 1, 2, 1)
ic.routingZoneInterconnect_draw()
ic.routingZoneInterconnectWorldCanvas_print()
----

=== Separate Geometry From Composition

When debugging visuals, ask the question in the right layer:

- `ki.kernelAreas_get().draw("pixel")` answers geometry ownership
- `z.routingZone_draw()` answers zone schematic structure
- `z.routingZoneWorldCanvas_print()` answers final local composition
- `world.canvas_print()` answers full composed output

== Practical Loop

A good inspection loop for geometry/render questions is:

[source,python]
----
z = zones.routingZone_get(1, 1)
z.routingZone_print()
z.routingZoneAreas_get()['intra'].draw("pixel")
z.routingZoneWorldCanvas_print()
z.routingZoneRoutesDraw_print()
world.canvas_print()
----

That moves from:

- summary
- to owned geometry
- to local composed output
- to local solved routes
- to full world composition

which is usually the shortest path to the real bug.
