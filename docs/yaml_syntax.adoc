= SignalFlow YAML Syntax Guide
Rudolph Pienaar <rudolph.pienaar@childrens.harvard.edu>
v2.0, March 2026

== Purpose

This document defines the YAML accepted by the current SignalFlow renderer.
It is derived from the implementation in `src/signalflow/models/node.py`,
`src/signalflow/config.py`, and `src/signalflow/engine/render.py`, with
examples cross-checked against `examples/`.

This guide distinguishes between:

- *Canonical syntax* — the form new YAML should use.
- *Backward-compatible syntax* — older forms still accepted by the parser.
- *Stale syntax* — forms that appear in older examples or tests but are not
  accepted by the current parser and should not be used.

== Top-Level Document

A SignalFlow document is a YAML mapping with these top-level keys:

- `title` — optional string displayed above the rendered diagram.
- `config` — optional per-document rendering overrides.
- `tree` — optional root node object.

For backward compatibility, the root node may also appear directly at the top
level with no `tree:` wrapper.  The renderer loads the root node with:

----
root = Node.node_fromDict(treeDict.get('tree', treeDict))
----

Canonical form:

[source,yaml]
----
title: "Optional diagram title"
config:
  channelWidth: 30

tree:
  module: App.ts
  func: "main()"
  calls: []
----

Backward-compatible form:

[source,yaml]
----
title: "Optional diagram title"
module: App.ts
func: "main()"
calls: []
----

== Root Node Grammar

Every node in the nested YAML structure is a mapping.

Required fields:

- `module` — string. Source file, module, or service name.
- `func` — string. Function label to render. By convention this includes
  parentheses, for example `"main()"` or `"process()"`.

Optional fields:

- `calls` — ordered list of child node objects. Defaults to empty.
- `input_ports` — ordered list of input port objects.
- `output_ports` — ordered list of output port objects.
- `internal_wiring` — ordered list of wiring strings.
- `chip_io` — per-node rendering override block.

Canonical node example:

[source,yaml]
----
module: Adapter.ts
func: "transform()"
input_ports:
  - signal: "input"
    return: "output"
output_ports:
  - signal: "payload"
    return: "result"
internal_wiring:
  - "input:payload"
  - "result:output"
calls:
  - module: Codec.ts
    func: "encode()"
    input_ports:
      - signal: "payload"
        return: "result"
    calls: []
----

== Declaration And Reference Semantics

The nested YAML surface should not be read as "every syntactic occurrence is a
new chip object."

The new-engine rule is:

- a full earlier `module` + `func` block declares a canonical chip
- a later short `module` + `func` block references that canonical chip
- repeated short references do not clone chips
- each `calls:` entry still creates a call edge in the circuit graph

This means:

- `process()` calling `process()` is one chip with a self edge
- a deeper node calling `root()` is a back-edge to the already declared
  `root()` chip
- a short later `Hub.ts` / `process()` reference inherits the earlier fuller
  declaration for ports, `internal_wiring`, `chip_io`, and child calls

Example:

[source,yaml]
----
tree:
  module: Hub.ts
  func: "process()"
  input_ports:
    - {signal: "a", return: "b"}
  calls:
    - {module: Hub.ts, func: "process()"}
----

This does not define two `process()` chips. It defines one canonical
`process()` chip with one self-call edge.

Conflict rule:

- if a later occurrence of the same `module` + `func` redefines previously
  declared metadata with different values, the parser rejects the document
  rather than silently merging incompatible declarations

== Port Syntax

`input_ports` and `output_ports` are lists of port objects.  A port object is a
mapping with these optional keys:

- `signal` — forward-call label.
- `return` — return-path label.

Port object example:

[source,yaml]
----
input_ports:
  - signal: "request"
    return: "response"
----

Port order matters. The parser binds ports by list position during
canonicalization and call-edge ordering.

== Internal Wiring

`internal_wiring` is a list of strings.  Each string has one of these forms:

- `"src:dst"`
- `"src:dst:data"`
- `"src:dst:thread"`
- `"src:dst:pure"`
- `"src:dst:compute"`
- `"src:dst:EW"`
- `"src:dst:WE"`
- `"src:dst:NS"`
- `"src:dst:SN"`
- `"src:dst:EW:pure"` (same for `WE`, `NS`, `SN`)
- `"src:dst:EW:compute"` (same for `WE`, `NS`, `SN`)
- `"src:dst:EW:thread"` (same for `WE`, `NS`, `SN`)
- `"src:dst:EW:data"` (same for `WE`, `NS`, `SN`)
- `"src:dst:...:color(name)"`

Meaning:

- `src` is always the source endpoint.
- `dst` is always the destination endpoint.
- `EW | WE | NS | SN` is an optional ordered source-to-destination orientation
  token.
- `:thread` marks the route as execution-thread wiring.
- `:data` marks the route as data / dependency wiring.
- `:pure` marks a thread route as a pure relay with no computation block glyph.
- `:compute` explicitly affirms compute semantics on a thread route.
- `:color(name)` is an optional per-route presentation modifier.

Examples:

[source,yaml]
----
internal_wiring:
  - "request:payload"
  - "request:payload:data"
  - "request:payload:thread"
  - "cipher:response"
  - "request:payload:compute"
  - "ready:ready:pure"
  - "constructedDecl:constructedDecl:EW"
  - "color:color:NS"
  - "request:payload:EW:color(red)"
  - "request:payload:EW:thread:compute:color(none)"
----

Notes:

- `internal_wiring` absent or empty means the chip is treated as an opaque
  transformation, not a manifold.
- Wiring names should match names declared in `input_ports` and `output_ports`.
- `internal_wiring` should be read as a declarative internal wiring netlist.
  It can declare both data/dependency routes and explicit execution-thread
  routes.
- `:thread` and `:data` do not change routing geometry. They only change route
  semantics and appearance.
- `:thread` with neither `:pure` nor `:compute` defaults to compute semantics.
- `:pure` and `:compute` are semantic modifiers for thread routes and are
  mutually exclusive.
- `:data` may not be combined with `:pure` or `:compute`.
- At most one `color(name)` modifier may be attached to a route.
- Supported colors are `red`, `green`, `yellow`, `blue`, `magenta`, `cyan`,
  `white`, `accent`, `muted`, and `none`.
- `:color(none)` forces that one route to render without ANSI color even when
  internal wiring colorization is enabled globally.
- The label order never changes: `<a>:<b>:SN` still means `a` is the source and
  `b` is the destination.  The orientation token constrains where those ordered
  endpoints must land.
- Orientation tokens are optional and override endpoint inference when present:
  `WE` = west-to-east cross-wall, `EW` = east-to-west cross-wall,
  `NS` = north-to-south same-wall, `SN` = south-to-north same-wall.
- Use an orientation token whenever the same display label appears on multiple
  possible endpoints, for example `constructedDecl:constructedDecl:EW` or
  `color:color:NS`.
- A right-wall `ret -> sig` handoff may trigger the renderer's
  *east-edge manifold reuse pattern*: when both endpoints already have east-side
  manifold bundles, the handoff is realized as a short local bridge that reuses
  those bundles instead of drawing a detached loop.

== `chip_io` Per-Node Overrides

Nodes may override the input-port model with:

[source,yaml]
----
chip_io:
  input:
    explicit: false
----

Currently supported per-node key:

- `chip_io.input.explicit` — boolean.
- `chip_io.internal_wiring.colorize` — boolean.
- `chip_io.internal_wiring.showInternalLabels` — boolean.
- `chip_io.internal_wiring.aliasInternalLabels` — boolean.

If omitted, the renderer falls back to the global config value
`config.chipIoInputExplicit`, which now defaults to `false`.

For the internal-wiring display keys, omission means “inherit the current
document/global renderer config for this chip.”

Example:

[source,yaml]
----
chip_io:
  input:
    explicit: true
  internal_wiring:
    aliasInternalLabels: true
    colorize: false
----

== `config` Syntax

The per-document `config` block is merged into the live renderer config before
parsing the tree.

Canonical top-level config keys:

- `channelWidth` — integer
- `verticalChipPadding` — integer
- `implicitThread` — string

Canonical nested config keys:

- `internal_wiring.colorize` — boolean
- `internal_wiring.shareRoutes` — boolean
- `internal_wiring.portSpacing` — integer
- `internal_wiring.passThroughAllowed` — boolean
- `internal_wiring.showInternalLabels` — boolean
- `internal_wiring.aliasInternalLabels` — boolean
- `internal_wiring.anchorLabelWidth` — integer
- `chip_io.input.explicit` — boolean

Default input behavior is sovereign (`false`) unless the document or chip
explicitly opts into per-caller west-side rows.

Canonical config example:

[source,yaml]
----
config:
  channelWidth: 30
  verticalChipPadding: 4
  implicitThread: block
  internal_wiring:
    colorize: true
    shareRoutes: false
    portSpacing: 10
    passThroughAllowed: true
    showInternalLabels: true
    aliasInternalLabels: false
    anchorLabelWidth: 0
  chip_io:
    input:
      explicit: true
----

Backward-compatible flat config keys still accepted:

- `internalWireColorize`
- `portVerticalSpacing`
- `shareInternalRoutes`
- `share_internal_routes`
- `passThroughAllowed`
- `showInternalLabels`
- `show_internal_labels`
- `aliasInternalLabels`
- `alias_internal_labels`

New YAML should prefer the canonical nested form.

Internal labels are a display policy, not a routing identity requirement. See
`docs/internalLabelDisplay.adoc` for the width and aliasing contract.

== Backward-Compatible Port Shorthand

The current parser still accepts the older single-port shorthand fields:

- `input_signal`
- `input_return`
- `output_signal`
- `output_return`

These are normalized internally into one-element `input_ports` or
`output_ports` lists.

Example:

[source,yaml]
----
module: App.ts
func: "main()"
output_signal: "args"
output_return: "result"
calls:
  - module: App.ts
    func: "run()"
    input_signal: "args"
    input_return: "result"
    calls: []
----

This shorthand is accepted, but new YAML should use `input_ports` and
`output_ports`.

== Stale or Unsupported Syntax

The following forms appear in some historical examples or tests but are *not*
accepted by the current parser in `Node.node_fromDict()`:

- `signal`
- `return_signal`

Do not use them in new YAML.  Replace them with canonical forms:

- `signal` -> `input_ports` or `output_ports`, depending on intent
- `return_signal` -> `input_return` / `output_return` shorthand, or preferably
  `input_ports` / `output_ports`

For example, do not write:

[source,yaml]
----
module: App.ts
func: "main()"
signal: "args"
----

Write instead:

[source,yaml]
----
module: App.ts
func: "main()"
output_ports:
  - signal: "args"
    return: "result"
----

== Shared Nodes and Repeated Calls

The parser canonicalizes nodes by the pair:

----
"{module}:{func}"
----

Consequences:

- Repeating the same `(module, func)` in multiple branches refers to one shared
  logical chip in the rendered graph.
- Repeated calls to the same child are preserved in call order using the
  internal `PortKey` mechanism.
- Port lists are bound by occurrence order, so declaration order in YAML is
  semantically significant.

This means YAML authors can declare a shared hub once with full ports and
`internal_wiring`, then reference it again later with a short call object:

[source,yaml]
----
- module: Proxy.ts
  func: "p2()"
  input_ports: [{signal: "s2", return: "r2"}]
  calls:
    - module: Hub.ts
      func: "process()"
----

If `Hub.ts:process()` was already declared elsewhere with full port metadata,
that metadata is reused and merged.

== Minimal Valid Examples

Leaf:

[source,yaml]
----
module: Leaf.ts
func: "work()"
calls: []
----

Single parent and child:

[source,yaml]
----
title: "Single Call"
tree:
  module: App.ts
  func: "main()"
  output_ports:
    - signal: "args"
      return: "result"
  calls:
    - module: Worker.ts
      func: "run()"
      input_ports:
        - signal: "args"
          return: "result"
      calls: []
----

Manifold chip:

[source,yaml]
----
title: "Manifold"
tree:
  module: App.ts
  func: "main()"
  output_ports:
    - signal: "raw"
      return: "done"
  calls:
    - module: Adapter.ts
      func: "adapter()"
      input_ports:
        - signal: "raw"
          return: "done"
      output_ports:
        - signal: "payload"
          return: "ready"
        - signal: "cipher"
          return: "sealed"
      internal_wiring:
        - "raw:payload"
        - "ready:cipher"
        - "sealed:done"
      calls:
        - module: Codec.ts
          func: "encode()"
          input_ports:
            - signal: "payload"
              return: "ready"
          calls: []
----

== Practical Authoring Rules

- Use `tree:` at the top level for all new documents.
- Use `input_ports` and `output_ports` for all new documents.
- Always include `calls: []` on leaves for clarity.
- Treat `module` + `func` as the node identity; changing either creates a
  distinct chip.
- Keep port order stable because binding is positional.
- Use `internal_wiring` only when you want explicit manifold routing semantics.
- Use orientation tokens when the same label exists on both walls or both ends
  of a same-wall handoff.
- Use `:pure` only when you want a pure relay with no computation block.
