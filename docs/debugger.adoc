== Purpose

The debugger is the primary design instrument for the live SignalFlow engine.

That point matters. The project does contain other render surfaces, but those surfaces should not be treated as the place where geometry or routing meaning is invented. The debugger REPL is the place where solved state is inspected, compared, and made precise.

The intended workflow is:

- build the typed document and selected overlap-zone solved route layers
- inspect those layers through the REPL
- refine chip, board, and selected zone surfaces until they express the
  intended visual grammar clearly
- only then treat a higher-level render as canonical

So the REPL is not a side utility. It is the shared mechanism by which routing and rendering questions should be answered.

== Role In The Current Architecture

The debugger should now be understood correctly:

- it is the primary interactive inspection surface
- it is not the primary owner of routing geometry

The board-era migration changed that boundary.

Current ownership is:

- `CallingStack` plus `zone_local.py`
  own the active adjacent-band overlap-zone topology
- local `RoutingZone` objects
  own selected-zone placement and local solve context
- `signalflow.board`
  owns routing substrate, effective geometry, realization-facing geometry,
  and board-backed render composition
- the debugger REPL
  adapts those typed models into an inspection-oriented operator surface

This means the debugger is where routing truth is observed, not where it should be re-derived from scratch.

== What Gets Built

The debugger materializes the current new-engine pipeline through the current solved-route layers.

At a high level:

1. `CircuitDocumentSource`
2. `CircuitDocument`
3. `SignalFlowConfig`
4. `RoutingZoneGrid`
5. placement / assignment state
6. route obligations
7. solved route layers
8. board models derived from zone/kernel scope
9. board-backed solver / realization / render inspection

So the REPL is not merely parsing YAML. It is exposing the actual typed engine state that later rendering must respect.

== Canonical Inspection Order

The intended debugger-first inspection order is:

1. chip
2. board
3. zone
4. selected overlap zone materialization

That order matters.

- chip rendering and terminal surfaces constrain local geometry
- board geometry constrains solve and realization
- selected-zone state constrains local continuity
- full-world overlap composition is downstream and intentionally not active until independent zones are correct

In particular, board inspection should now sit between chip and zone whenever the question is about routing geometry, label clearance, boundary ownership, or materialized wire placement.

== Current Board-Backed Workflow

For a local routing scope:

[source,python]
----
zone = zones.zone_get(1, 1)
kernel = zone.kernel_get("intra")

board = kernel.board_get()
substrate = board.substrate_get()
effective = board.effective_get()
----

This gives three important inspection surfaces:

- the operational effective board
- the raw substrate comparison board
- the zone that owns the broader world/topology context

Typical board questions are now answered through:

[source,python]
----
board.geometry_text(columnOffset=0)
board.boundaries_get()
board.terminal_get("App.ts.main()", "s1")
board.validation_text()
----

== Current Materialization Workflow

The materialized route render should be inspected from the same board that constrained the solve.

[source,python]
----
solver = kernel.solver_get(board)
solution = solver.solution_get()
materialized = solution_realize(board, solution)
----

Then inspect:

[source,python]
----
materialized.summary_text()
materialized.wiring_text()
materialized.geometry_text()
materialized.algebraicWorld_text("App.ts.main().s1")
----

This is now the preferred path for questions such as:

- did the effective geometry move the chip and terminal together
- does the realized route actually land on the exact terminal
- is the module boundary outside the long channels
- are wires under a module boundary

== Collision Inspection

Collision inspection is now first-class on the materialized handle.

[source,python]
----
materialized.collisions_text()
materialized.boundaryViolations_text()
materialized.occupancyViolations_text()
----

The important practical shift is that geometric violations can now be inspected from first-class board geometry plus realized route cells rather than guessed from a suspicious artifact alone.
