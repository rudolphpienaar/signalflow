== Status

This document collects architectural ideas and design candidates that are worth preserving, but are not yet accepted as current implementation truth.

Use this document for:

- future-direction notes
- candidate semantics
- possible API improvements
- ideas discovered during debugging or redesign work

Do not treat the contents of this document as implemented behavior unless a separate current-truth document says so.

== Explicit Call-To-Port Binding

=== Problem

The current YAML model allows a chip to declare multiple `input_ports` and `output_ports`, while call-site binding still defaults to implicit occurrence-order assignment.

This is logically coherent, but it is not fully explicit.

For example, in the legacy interpretation:

- the first incoming call to a chip binds to the first declared input pair
- the second incoming call binds to the second declared input pair
- and so on

This works, but it means semantic binding is carried partly by call order rather than by an explicit edge-to-port declaration.

The situation is made harder to read when rendering policy hides some of the declared input surface, for example when:

- `chip_io.input.explicit: false`

In that case the binding still exists semantically, but the full bound port surface may not be materially shown on the rendered chip.

=== Candidate Direction

Add an optional explicit call-site binding declaration.

Possible shape:

[source,yaml]
----
calls:
  - module: Hub.ts
    func: "process()"
    bind_input:
      signal: "s3"
      return: "r3"
----

Meaning:

- this call is explicitly bound to the `s3/r3` input pair on the child chip

The intended resolution rule would be:

- if explicit binding is present, use it
- otherwise fall back to the current occurrence-order rule

This preserves backward compatibility while making the semantic mapping easier to inspect and reason about.

=== Separation Of Concerns

This idea is also an argument for separating:

- semantic port binding
- render-time port materialization

Those are related, but they are not the same question.

Semantic binding asks:

- which declared port pair does this call use?

Render materialization asks:

- which declared port pairs are visibly surfaced on the chip wall?

Keeping those concerns distinct would reduce ambiguity in both documentation and implementation.

=== Current Status

This is an idea only.

The current implementation still relies on implicit occurrence-order binding as the default model.

== Chip Stack Placement Policy

=== Problem

Chip stacks on opposite sides of a kernel can be materially asymmetric.

For example:

- one chip on the west side
- many chips on the east side

Top-aligning both sides is mechanically simple, but it can produce a lopsided visual result and an unbalanced fan structure even when the routing geometry is otherwise legal.

=== Candidate Direction

Expose a configurable chip stack placement policy at the board/kernel level.

Possible values:

- `north`
- `south`
- `centroidal`

Intended meaning:

- `north`: stack starts from the north/top edge of the terminal band
- `south`: stack starts from the south/bottom edge of the terminal band
- `centroidal`: stack is positioned so the used chip-set centroid is balanced
  within the available terminal band

This should be treated as board construction or placement doctrine, not solver doctrine.

=== Current Status

This is an idea only.

The implementation currently uses one active placement doctrine rather than an operator-selectable placement policy surface.

== Symmetric Band Relaxation Policy

=== Problem

Earlier the realization relaxation was pressure-driven and one-sided.  If the north latitude family moved upward to avoid realized overlap, the south latitude family could remain where it was.  This was geometrically valid but visually asymmetric.

=== Current Status (v6.0.7)

The relaxation is now paired by construction.  `_regionFramesShifted_build` emits one paired step per iteration: `Ni.verticalStart -= 1` together with `Si.verticalStart += 1`, plus the corresponding north/south transition bands.  `BoardRelaxationSymmetry.MINIMAL` and `BoardRelaxationSymmetry.SYMMETRIC` therefore behave the same for centroid spread and are parked for later design cleanup.

The scoring function that drives the loop is itself the policy lever: `_realizedCollisionCount_calculate` weights collisions on chip-terminal entry rows higher (penalty 2 vs 1), so the relaxation prefers spreads that push collisions off rows pinned by chip placement.  Signal IDs are extracted from the path text's trailing `.NAME` token (robust across both annotated `[id=]` and bare formats), so legitimate same-signal multi-drop fanout no longer counts as collision.

The current world-scale extraction work preserves this local relaxation policy but derives vertical zone offsets from shared seam chip rows.  The north relaxation budget includes `Ne + Nt + Nfi`; the older north-stack-only interpretation is not the current world-origin rule.

Forward-only omitted-return ports are no longer an open modeling question. Future ideas should treat missing `return` as a true one-lane declaration, not as a paired return lane with an empty label.

The remaining open question is whether to expose an asymmetric mode for cases where Ni and Si have different headroom against their respective hard bounds.  No active blocker requires it.
