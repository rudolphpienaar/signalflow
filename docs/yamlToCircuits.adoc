== Purpose

NOTE: This document still contains historical seam/interconnect pipeline language. The active April 2026 workflow for overlap work is per-zone synthetic materialization through `src/signalflow/engine/inspect/zone_local.py`. Do not treat old composed-world or seam solver sections as current implementation targets.

This note captures the current end-to-end development workflow of the new
SignalFlow engine, beginning with one YAML source file and ending, for now, at
the first explicit grid-level solved-route layer.

It exists to answer one practical question clearly:

_What exactly happens, conceptually and structurally, after a YAML document is
loaded?_

The short answer is that the new engine no longer jumps from YAML directly into
rendering heuristics. It passes through a sequence of typed models, each with a
clear owner and a clear responsibility, and it now produces real solved
artifacts before final render language exists.

One clarification now matters:

- top-level composed-world rendering is intentionally disabled under the overlap-zone architecture
- the debugger and snippet surfaces are the primary mechanism for discovering the selected-zone render grammar

So the intended workflow is:

- first build solved truth
- then inspect and refine draw/print surfaces in the debugger
- then, only later, promote those conventions into the final presentation
  renderer

The immediate active work therefore sits at the per-zone inspection boundary:

- materialize one overlap zone at a time
- inspect `back-and-forth.yaml` zones `1,1`, `1,2`, and `1,3`
- fix zone-local wiring and realization before attempting full-board overlap integration

That figure is deliberately linear even though the eventual solver is not. The
important point is that each stage hands off a resolved model rather than a
half-inferred bag of local state. The debugger then becomes the place where
those resolved models are interrogated until the correct presentation language
is clear.

That interrogation order is now deliberate:

1. `Chip`
2. `RoutingZone`
3. `RoutingZoneInterconnect`
4. `RoutingZoneGrid`

The order matters because chip render geometry is upstream of the later
container geometry.

== Stage 0: Raw YAML

The process begins with one raw YAML document loaded as a Python mapping.

[source,yaml]
----
title: "example"
tree:
  module: App.ts
  func: "main()"
  calls:
    - module: Worker.ts
      func: "run()"
      calls: []
----

At this boundary, the data is still untyped and untrusted.

This is the only place in the new engine where anonymous dictionaries are
allowed to exist as the main document representation.

== Stage 1: Serialized Source Models

The first typed boundary is the source-model layer:

- `CircuitDocumentSource`
- `CircuitNodeSource`
- `CircuitPortDeclarationSource`
- `CircuitWiringDirectiveSource`
- `CircuitChipIoSource`

These models still mirror the serialized YAML shape closely. That is
intentional. Their job is not to reinterpret the circuit yet. Their job is to
stop raw dictionaries from leaking inward.

[source,text]
----
  ┌───────────┐
  │ YAML tree │
  └───────────┘
        │
        ▼
  ┌────────────────────┐
  │ typed source mirror│
  └────────────────────┘
        │
        ├── module / func / calls
        ├── input_ports / output_ports
        ├── internal_wiring
        └── chip_io
----

This stage answers:

- is the document structurally well-formed
- are strings really strings
- are lists really lists
- are optional blocks really mappings when present
- is shorthand normalized into one source representation

It does not yet answer:

- where chips live in the world
- how routes are solved
- what geometry a zone should have

== Stage 2: Validated Circuit Models

The next stage converts source models into validated circuit models:

- `CircuitDocument`
- `CircuitCallSet`
- `CircuitChipSet`
- first-class `Chip`

This is the point where the engine begins to represent the circuit as a real
domain model rather than a serialized document.

[source,text]
----
  ┌──────────────────────┐
  │ CircuitDocumentSource│
  └──────────────────────┘
              │
              ▼
  ┌────────────────────┐
  │ CircuitDocument    │
  └────────────────────┘
              │
              ├── canonical Chip objects
              ├── explicit ordered call edges
              └── CircuitChipSet
----

This stage does several important things.

First, it separates declaration identity from call/reference structure.

That means repeated short `(module, func)` references are not treated as cloned
chip occurrences. They become additional call edges to one canonical chip.

So:

- a full earlier declaration defines the canonical chip
- a later short occurrence references that chip
- recursion becomes a self edge
- back-calls become edges to already-declared chips

Second, chip-local declarations are gathered into the `Chip` model:

- input-port declarations
- output-port declarations
- declarative `internal_wiring`
- optional `chip_io` overrides

Third, chip terminals are synthesized explicitly from those declarations. The
engine no longer treats terminal identity as something to rediscover much later
during layout or rendering.

The same stage now also separates canonical terminal identity from display-only
wall aliases.

The engine carries:

- canonical terminal ids, which come from the declared `input_ports` and
  `output_ports`
- display-only output wall aliases, which may come from `bind_output`

`bind_output` changes the wall text shown on the source chip for one outgoing
call stage. It does not change the canonical terminal id used for routing,
attach lookup, or board terminal ownership.

So a call may now legitimately appear as:

- source chip display label: `c1ret`
- source canonical terminal id: `p2sig`
- destination chip display label: `p2sig`
- destination canonical terminal id: `p2sig`

The important architectural rule is that display labels are presentation
traits, while terminal ids remain semantic identity.

So this stage answers:

- what the circuit is
- what canonical chips exist
- what call edges exist between them
- what each chip declares locally

=== Canonical Identity Versus Display Alias

One subtle but important detail of the current engine is that output display
aliases are resolved during chip build, not later in board reporting.

The current model therefore has three distinct artifacts:

- `Chip.outputPortDeclarationSet`
- `Chip.outputDisplayPortDeclarationSet`
- `ChipTerminalSet`

The first owns canonical output ids. The second owns display-only east-wall
labels. The third is synthesized from the canonical declarations and therefore
remains routing-facing truth.

This means a useful debugging rule is now available:

- if attach lookup fails, check canonical terminal ids
- if the wall text looks wrong, check display declarations

Do not collapse those two problems into one.

== Stage 3: Validated World Configuration

In parallel with the circuit model, the engine builds the world-configuration
model:

- `SignalFlowConfig`
- `RoutingZoneGridConfig`

This stage defines the intended topology regime of the solve.

[source,text]
----
  ┌──────────────────────┐
  │ YAML document/config │
  └──────────────────────┘
            │
            ▼
  ┌────────────────────┐
  │ SignalFlowConfig   │
  └────────────────────┘
            │
            ├── world sense
            ├── grid dimensions
            ├── path policy
            └── channel sense
----

Conceptually, this stage answers:

- what kind of world are we solving in
- how many routing zones exist
- what is the major propagation sense
- what macro pathing policy applies

This is a different question from the circuit question. The circuit says what
software structure exists. The world config says what routing world we want to
embed that structure into.

== Stage 4: Empty World Topology

From the validated world config, the engine builds an empty `RoutingZoneGrid`
topology skeleton.

That skeleton contains:

- `RoutingZone` identities
- `RoutingZoneInterconnect` identities
- `gridSize`
- direct coordinate-based lookup

It does not yet contain chip placement or route solve results.

[source,text]
----
  ┌────────────────────┐
  │ SignalFlowConfig   │
  └────────────────────┘
            │
            ▼
  ┌──────────────────────────┐
  │ RoutingZoneGrid skeleton │
  └──────────────────────────┘

    ┌─────┐                                     ┌─────┐
    │[1,1]├─────────────────────────────────────┤[2,1]│
    └─────┘                                     └─────┘
        \_____ interconnect([1,1] <-> [2,1]) _____/
----

This stage answers:

- where routing zones exist in the world
- which zones are neighbors
- what macro zone-to-zone paths are possible

This is the first explicit world model.

Important identity rule:

- `RoutingZone`s have grid coordinates such as `[1,1]` and `[2,1]`
- a `RoutingZoneInterconnect` does not get its own grid coordinate
- an interconnect is identified by the pair of zones it connects

== Stage 5: Circuit-to-World Assignment

Once the engine has both:

- a validated circuit
- a world topology

it can build the assignment bridge:

- `RoutingZoneAssignmentSet`
- `RoutingZoneLayerSet`

This stage maps canonical chips into routing zones according to the current
simple major-axis regime.

[source,text]
----
  ┌──────────────────┐      ┌──────────────────┐
  │ CircuitDocument  │      │ RoutingZoneGrid  │
  └──────────────────┘      └──────────────────┘
            ╲                    ╱
             ╲                  ╱
              ╲                ╱
               ▼              ▼
            ┌────────────────────┐
            │ assignment builder │
            └────────────────────┘
                      │
                      ▼
            ┌──────────────────────────┐
            │ RoutingZoneAssignmentSet │
            └──────────────────────────┘

    canonical chip ──▶ owning zone ──▶ terminal side
----

For the current simple West-to-East regime, the mapping rule is:

- depth 0 -> zone 1 west side
- depth 1 -> zone 1 east side
- depth 2 -> zone 2 west side
- depth 3 -> zone 2 east side

and similarly for the North-to-South simple regime:

- depth 0 -> zone 1 north side
- depth 1 -> zone 1 south side
- depth 2 -> zone 2 north side
- depth 3 -> zone 2 south side

This stage answers:

- which routing zone owns this chip occurrence
- which terminal side of that zone the chip belongs to

It does not yet answer:

- the final geometry of the zone
- the final route geometry

== Stage 6: Logical Placement Planning

The next stage enriches the world with a logical placement plan.

This is the output of:

- `signalflow.routing.placement`

The planner rebuilds the `RoutingZoneGrid` with explicit local planning data:

- `ChipPlacementSet`
- logical `RoutingZoneFrame`
- logical `RoutingZoneInterconnectFrame`
- explicit owned `RoutingZoneRegion` geometry

[source,text]
----
  ┌──────────────────────────┐
  │ RoutingZoneAssignmentSet │
  └──────────────────────────┘
               │
               ▼
  ┌───────────────────────────┐
  │ placement planner         │
  └───────────────────────────┘
               │
               ▼
  ┌───────────────────────────┐
  │ placed RoutingZoneGrid    │
  │ logical planning geometry │
  └───────────────────────────┘

    ┌────┬──────┬─────┬──────┬──────┬────┐
    │ IF │ CHIP │ IFO │ ILON │ CHIP │ EF │
    └────┴──────┴─────┴──────┴──────┴────┘
----

The important point is that this is not fake final geometry.

It is planning geometry:

- explicit enough that later routing phases can consume it
- conservative enough that it does not claim the full route solve already exists

So this stage answers:

- what local regions a zone owns
- what order chips occupy a terminal region in
- what the logical outer frame of a zone is
- what the logical frame of an interconnect seam is

== Stage 7: Route Obligations

The next stage derives the first explicit routing-input model from:

- `CircuitDocument`
- placed `RoutingZoneGrid`

The output is:

- `RouteObligationSet`
- `CallRouteObligationSet`
- `ChipInternalRouteObligationSet`

[source,text]
----
  ┌────────────────────┐      ┌───────────────────────────┐
  │ CircuitDocument    │      │ placed RoutingZoneGrid    │
  └────────────────────┘      └───────────────────────────┘
            ╲                           ╱
             ╲                         ╱
              ╲                       ╱
               ▼                     ▼
            ┌────────────────────────────┐
            │ route-obligation builder   │
            └────────────────────────────┘
                         │
                         ▼
            ┌────────────────────────────┐
            │ RouteObligationSet         │
            └────────────────────────────┘

    call edge          ──▶ call route obligation
    internal_wiring    ──▶ chip-internal obligation
----

This stage is intentionally coarse. It does not yet solve geometry. It only
states what connectivity must be realized and what geometric scope that
obligation belongs to.

Current scopes are:

- `CHIP_INTERNAL`
- `ZONE_LOCAL`
- `SEAM_CROSSING`
- `GRID_LONG_HAUL`

So this stage answers:

- which parent-to-child calls become routing work
- which chip-local `internal_wiring` declarations become routing work
- whether a call stays inside one zone, crosses one seam, or must travel across
  a longer grid path

It still does not answer:

- exact lane selection
- exact turn geometry
- exact seam handoff coordinates

== Stage 8: Chip-Local Solve

The first solved route layer now exists for chip-internal routing.

Current solved artifact:

- `ChipInternalSolvedRouteSet`

This stage takes:

- `CircuitDocument`
- `ChipInternalRouteObligationSet`

and produces solved chip-local routes that:

- parse each `internal_wiring` directive into a typed directive spec
- resolve directive endpoints against canonical chip terminals
- infer default source/destination sides from chip declaration roles when
  orientation is omitted
- prefer input-declared terminals for source endpoints
- prefer output-declared terminals for destination endpoints
- classify each internal route as either:
  - `TRANSVERSE_MANIFOLD`
  - `SAME_SIDE_INTERNAL`

[source,text]
----
  ┌────────────────────────────┐
  │ ChipInternalRouteObligation│
  └────────────────────────────┘
                │
                ▼
  ┌────────────────────────────┐
  │ ChipInternalSolvedRoute    │
  └────────────────────────────┘
                │
                ├── parsed directive spec
                ├── resolved source terminal
                ├── resolved destination terminal
                ├── concrete chip-local routing owner
                └── first solve-kind classification
----

This stage still does not answer:

- cell-by-cell manifold geometry
- exact internal track assignment
- final chip render geometry

What it does answer now is:

- which terminal pair each `internal_wiring` statement actually means
- whether a directive is same-side local continuity or a transverse manifold
  route
- whether omitted orientation can be recovered from chip declaration roles

This matters for the current simple-circuit corpus. Declarations such as
`tick:tick` and `tock:tock` are intentionally legal. In the current solver they
resolve by chip declaration role, not by cloning chip occurrences and not by
guessing from nested YAML position.

== Stage 9: Zone-Local Solve

The next solved route layer now exists for `ZONE_LOCAL` call obligations.

Current solved artifact:

- `RoutingZoneLocalSolvedRouteSet`

This stage takes:

- `CircuitDocument`
- placed `RoutingZoneGrid`
- `CallRouteObligationSet`

and produces solved zone-local routes that:

- select the owning placed `RoutingZone`
- resolve the source and destination `ChipPlacement`s in that zone
- consume the actual planned `RoutingZoneRegionFrame` geometry already produced
  by placement planning
- emit explicit world-coordinate route points through the zone
- classify each local route as either:
  - `CLOCKWISE_INTRA_FORWARD`
  - `CLOCKWISE_INTRA_RETURN`
  - `INTER_PERIMETER_FORWARD`
  - `INTER_PERIMETER_RETURN`

[source,text]
----
  ┌──────────────────────────┐      ┌───────────────────────────┐
  │ CallRouteObligationSet   │      │ placed RoutingZoneGrid    │
  └──────────────────────────┘      └───────────────────────────┘
                ╲                              ╱
                 ╲                            ╱
                  ▼                          ▼
               ┌───────────────────────────────┐
               │ zone-local route solver       │
               └───────────────────────────────┘
                               │
                               ▼
               ┌───────────────────────────────┐
               │ RoutingZoneLocalSolvedRouteSet│
               └───────────────────────────────┘
                               │
                               ├── owning zone id
                               ├── route point polyline
                               ├── traversed region ids
                               └── local solve-kind classification
----

This stage is solving for actual geometry, but at the planning-grid level.

That means:

- route points are real world coordinates derived from `RoutingZoneFrame` and
  `RoutingZoneRegionFrame`
- chip ordering inside terminal bands affects the actual route rows or columns
- route polylines are explicit and inspectable in the debugger

It does _not_ mean:

- final ASCII track rasterization already exists
- seam-crossing or long-haul routing is solved
- rendering decisions have been made

So the geometry is now real enough to debug structurally, but still one layer
above final projection.

== Stage 10: Interconnect Seam Solve

The next solved route layer now exists for `SEAM_CROSSING` call obligations.

Current solved artifact:

- `RoutingZoneInterconnectSolvedRouteSet`

This stage takes:

- `CircuitDocument`
- placed `RoutingZoneGrid`
- `CallRouteObligationSet`

and produces solved seam routes that:

- choose the owning `RoutingZoneInterconnect`
- consume the actual placed interconnect frame
- consume the neighboring `INTER_ROUTING_FAN_IN_OUT` region frames from the
  source and destination zones
- emit explicit seam route points in world coordinates
- classify each seam route as either:
  - `STRAIGHT_SEAM`
  - `OFFSET_SEAM`

[source,text]
----
  ┌──────────────────────────┐      ┌───────────────────────────┐
  │ CallRouteObligationSet   │      │ placed RoutingZoneGrid    │
  └──────────────────────────┘      └───────────────────────────┘
                ╲                              ╱
                 ╲                            ╱
                  ▼                          ▼
              ┌─────────────────────────────────┐
              │ interconnect seam solver        │
              └─────────────────────────────────┘
                                │
                                ▼
              ┌─────────────────────────────────┐
              │ RoutingZoneInterconnectSolved...│
              └─────────────────────────────────┘
----

This stage is also solving for actual geometry, again at the planning-grid
level rather than final rendering.

What it answers now:

- which interconnect owns one seam-crossing call
- which seam points carry that continuity
- whether the seam is straight or offset

What it still does not answer:

- zone-side seam half routes inside the neighboring zones
- final rendered projection

== Stage 10: Grid-Level Long-Haul Solve

The next solved layer is the first world-scale route realization:

- `RoutingZoneGridSolvedRouteSet`

This stage consumes `GRID_LONG_HAUL` obligations together with the already
placed world topology and the already solved macro path from `RoutingZoneGrid`.

[source,text]
----
  ┌──────────────────────────┐      ┌───────────────────────────┐
  │ CallRouteObligationSet   │      │ placed RoutingZoneGrid    │
  └──────────────────────────┘      └───────────────────────────┘
                ╲                              ╱
                 ╲                            ╱
                  ▼                          ▼
              ┌─────────────────────────────────┐
              │ grid long-haul solver           │
              └─────────────────────────────────┘
                                │
                                ▼
              ┌─────────────────────────────────┐
              │ RoutingZoneGridSolvedRouteSet   │
              └─────────────────────────────────┘
----

This is still planning-grid geometry rather than final rendered projection.

What it answers now:

- which multi-zone path realizes one long-haul call
- which interconnects that path traverses
- which world-coordinate points carry the route
- which intermediate zones participate in the path

What it still does not answer:

- final endpoint-local delivery inside the source/destination zones
- final rendered projection

== Where We Are Now

The current codebase is solid through the first explicit grid-level solved
route layer.

From one YAML document, the new engine can now build:

1. `CircuitDocumentSource`
2. `CircuitDocument`
3. `SignalFlowConfig`
4. empty `RoutingZoneGrid`
5. `RoutingZoneAssignmentSet`
6. logically placed `RoutingZoneGrid`
7. `RouteObligationSet`
8. `ChipInternalSolvedRouteSet`
9. `RoutingZoneLocalSolvedRouteSet`
10. `RoutingZoneInterconnectSolvedRouteSet`
11. `RoutingZoneGridSolvedRouteSet`

That means the new engine now has:

- typed circuit input
- typed world input
- explicit world topology
- explicit chip-to-zone ownership
- explicit logical placement planning
- explicit coarse routing obligations
- explicit first chip-local solved routes
- explicit first zone-local route geometry
- explicit first seam continuity geometry
- explicit first long-haul route geometry

The first structural corpus for this stage now exists under
`examples/simple-circuit/`. That fixture family is used to hold the graph
semantics steady for:

- self edges
- ancestor/back edges
- canonical depth assignment
- coarse route-obligation scope classification
- first chip-local solve behavior

The focused chip-solver tests also now hold steady the directive rules for:

- bare `src:dst` data routes
- implicit `thread -> compute` defaulting
- same-side local continuity
- explicit orientation disambiguation
- unknown endpoint rejection

The focused zone-solver tests now also hold steady the first zone-local route
geometry rules for:

- straight transverse root-to-child paths inside one zone
- row/column-offset local paths when terminal-band order differs
- same-side local self routes for recursive/self edges

== The Next Few Stages

The next conceptual stages are no longer parser or topology work. They are
solve work.

=== Stage 11: Rendering

The first planning projection now exists. It renders the solved world geometry
into a readable artifact for debugging and test locking.

That artifact now includes:

- one primary rendered diagram block
- compact zone topology with chip-placement summaries
- compact chip bodies inside that topology block
- compact port-face hints beneath those chip bodies
- an attached route row where routes visibly meet chip-face bodies
- a route canvas in world coordinates
- solved world-route summaries
- chip-internal route summaries

The primary `diagram:` block is intentionally row-labeled:

- `zone`
- `coord`
- `chip`
- `face`
- `link`
- `flow`

That keeps the artifact readable while the renderer is still in the planning
projection stage.

The `face` row remains declaration-oriented. The `flow` rows now render chip
cells from solved route contact, so the route band shows where the current path
actually touches each chip rather than only repeating the declaration-time face
hint.

For rectangular worlds, the `diagram:` is now assembled by world row. Each
grid-row topology block is followed immediately by the compacted route rows for
that same vertical band, then by a seam row that marks the handoff into the
next band, before the next grid-row block begins.

For horizontal rectangular worlds, that seam row now distinguishes plain
vertical continuation (`│`) from turning/branching handoff columns rendered
with directional tee/corner glyphs such as `┬`.

If the next lower band begins with a `link` row, those seam handoff stems are
now carried into that first `link` row too, so the lower-band attachment reads
as an explicit continuation rather than a fresh disconnected start.

For taller route runs in the `diagram:` block, the renderer now compacts the
route presentation intentionally:

- empty route rows may be omitted entirely
- `link` rows are shown only where a chip body actually attaches into the flow
- repeated vertical pass-through rows may be collapsed into an ellipsis marker

The separate `canvas:` section remains the uncompressed coordinate truth.

At present the renderer is strongest for:

- one-row `WestToEast` worlds
- one-column `NorthToSouth` worlds
- conservative rectangular worlds under the current serpentine major-axis
  traversal policy

That now includes grouped rectangular presentation for both horizontal-major and
vertical-major worlds.

True fully general 2D placement strategy is still a later engine stage, but
the pipeline now reaches a real rectangular-world artifact under the current
deterministic traversal policy.

What still does not exist is the final presentation renderer.

                           └──────────────┘
----

== Why This Workflow Matters

The value of this pipeline is not that it creates more files or more dataclasses.
Its value is that each stage answers one question and then stops.

Examples:

- source models answer "what did the YAML say"
- circuit models answer "what circuit exists"
- config answers "what world do we want"
- topology answers "what zones and seams exist"
- assignment answers "which zone owns which chip occurrence"
- placement planning answers "what local substrate exists before routing"
- route solving answers "what geometry carries the routing work"
- projection rendering answers "what the current solved world looks like"

That separation is what prevents the engine from drifting back into the old
pattern where final rendering heuristics rediscover topology and attachment
rules too late.
