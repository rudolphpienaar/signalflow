== Problem Statement

The current board-era work gives SignalFlow a strong local routing primitive:

- one kernel
- one local crossbar-like `intra` substrate
- symbolic solve first
- realization second

This works well for routing in the zone's primary sense. For `WTE`, that means:

- west-side chip terminals
- east-side chip terminals
- local directed obligations flowing through the kernel

The macro problem appears when the route is not aligned with the zone's sense. Examples:

- a child calls its parent
- a child calls itself recursively
- a route must travel across world scale rather than only inside one local kernel

These are not edge cases. They are part of the domain.

The design question is therefore:

- what geometric substrate should own against-sense and world-scale routing?

== Current Local Kernel

The current local kernel should be read as an `intra` routing core.

For `WTE`, its symbolic families are:

- west-side local longitudes
- north latitudes
- east-side local longitudes
- south latitudes

The important current point is not the exact token names. It is that `intra` is a disciplined local substrate for sense-aligned routing.

A simplified `WTE` kernel is:

[source,text]
----
west chips        local intra kernel                 east chips

  W terminals   wf ──▶ wLong ──▶ nLat ──▶ eLong ──▶ ef    E terminals
               ╱                                       ╲
              ╱                                         ╲
  W returns   wf ◀── wLong ◀── sLat ◀── eLong ◀── ef    E returns
----

This is good local doctrine. It is not enough for against-sense or recursive routing.

== The Wrong Simplification

A tempting thought is:

- if `intra` is a good routing primitive
- perhaps all reverse/global routing should be expressed by more kernels

Examples of this temptation:

- convert inter-zone seams into more kernels
- replace perimeter routing with neighboring implied kernels
- route reverse traffic by switching orientation in those neighboring kernels

This is attractive at first because it appears to reuse one primitive.

The problem is that it introduces new routing objects that are not actually native semantic objects in the source:

- seam kernels
- implied kernels
- virtual neighboring kernels

That localizes complexity in invented routing objects instead of in the real objects already present in the model:

- chips
- kernels
- explicit routing substrates

== The Proposed Distinction

The current synthesis suggests a simpler split:

- `intra`
  the kernel's primary sense-aligned routing core
- `extra`
  concentric perimeter routing substrates outside `intra`

The crucial point is:

- `extra` is not a new kernel
- `extra` is not a seam object
- `extra` is the same kernel's outer escape and world-scale routing substrate

In this model, one kernel owns one larger structure:

- inner `intra`
- outer `extra`
- transfer regions connecting them

== Why `extra` Exists

`extra` is motivated by three concrete route classes.

=== Child To Parent

A child on the east stack may need to route back to the parent-facing west side.

This is against the primary `WTE` sense.

`extra` solves it by allowing a route to:

- leave the east-side local context
- escape outward
- travel around the outer perimeter
- re-enter on the west side

=== Child To Self

A child may need to call itself recursively.

This is the route class that breaks several virtual-kernel stories.

Why it matters:

- the source child may be interior to a stacked east column, such as `p4()`
- the route must preserve local row identity strongly enough to leave from the
  `p4()` layer and re-enter `p4()` again
- the west-side re-entry target is not just "the parent side of the zone"

The perimeter `extra` substrate handles this more naturally because it can
carry a row-preserving escape path around the outer structure.

=== World-Scale Long-Haul

A route may need to travel beyond one local kernel or one local chip pair.

Instead of inventing a separate world-only routing species, the same `extra`
families can expand outward and carry larger-scale traffic as needed.

This is one of the strongest advantages of the model:

- local reverse routing
- recursive routing
- world-scale long-haul

all live in one symbolic outer substrate.

== Transfer Regions

`extra` cannot be useful if it is a disconnected ring.

The key doctrine is therefore:

- `intra` must transfer into `extra`
- `extra` must transfer back into `intra`

This transfer is not accidental. It must be first-class geometry.

For `WTE`, a canonical example is:

- `eLong` must be able to reach `xnLat`

That means there is an outward transfer geometry where a route can:

- travel in inner east-local longitude
- climb into the outer north perimeter

Likewise, there must be corresponding transfer geometries on:

- east to south
- west to north
- west to south

and potentially at the four corners of the outer perimeter if cross-world
traffic requires them.

So the full picture is not:

- inner core plus outer ring

but:

- inner core
- outer perimeter
- explicit transfer surfaces between them

== `sfN` Route Narratives

This section describes the intended symbolic reading in SignalFlow notation.

The exact token names may change, but the route stories should remain.

=== Sense-Aligned Local Forward

A normal `WTE` local route remains purely `intra`:

[source,text]
----
sf0:
  parent.west.signal
    ──▶ wf[0]
    ──▶ wLong[a]
    ──▶ nLat[b]
    ──▶ eLong[c]
    ──▶ ef[0]
    ──▶ child.east.signal
----

This is already the current regime.

=== Child To Parent

Against-sense routing escapes from `intra` to `extra`.

[source,text]
----
sf1:
  child.east.return
    ──▶ ef[0]
    ──▶ eLong[a]
    ──▶ xfer(eLong ──▶ xnLat)
    ──▶ xnLat[b]
    ──▶ xwLong[c]
    ──▶ xfer(xwLong ──▶ west return entry)
    ──▶ parent.west.return
----

The exact transfer tokens are not settled. What matters is that:

- the route can leave `intra`
- travel in `extra`
- and re-enter coherently

=== Child To Self

Self-routing uses the same outer perimeter substrate, but its semantics are
subtler because source and destination chip identities are the same.

[source,text]
----
sf2:
  p4.east.signal
    ──▶ ef[0]
    ──▶ eLong[a]
    ──▶ xfer(eLong ──▶ xnLat)
    ──▶ xnLat[b]
    ──▶ xwLong[c]
    ──▶ xfer(xwLong ──▶ p4 west-side re-entry)
    ──▶ p4.west.signal
----

This is intentionally written as:

- leave `p4` from the east-side local layer
- traverse `extra`
- return to `p4` on the west-side local layer

The important geometric requirement is:

- `extra` and its transfer surfaces must preserve enough row/layer identity to
  distinguish `p4` from `p1`, `p2`, `p3`, and `p5`

=== World-Scale Long-Haul

World-scale travel is the same story, simply with more `x*` carriers and
possibly repeated transfer points:

[source,text]
----
sf3:
  local intra exit
    ──▶ xfer(intra ──▶ extra)
    ──▶ x* perimeter carriers
    ──▶ xfer(extra ──▶ neighboring local substrate)
    ──▶ local intra re-entry
----

This is the unifying idea:

- `extra` should be able to scale from local reverse routing to global travel

== Capacity Coupling

One key insight from this model is:

- `extra` routes are not free with respect to `intra`

If a child calls itself, that route does not consume only outer-ring capacity.
It also consumes:

- an `intra` escape opportunity
- a transfer opportunity
- and a re-entry opportunity

So against-sense traffic can and should influence the sizing of the local
kernel's geometry.

This means:

- `intra` lane counts may need to grow to support `extra` transfers
- `extra` lane counts may need to grow for long-haul or recursive demand

The likely doctrine is therefore demand-driven sizing of both:

- inner `intra`
- outer `extra`

== Why This Is Better Than Virtual Kernels

The virtual-kernel idea was attractive because it appeared to reuse the kernel
primitive for reverse routing.

The present conclusion is that `extra` is cleaner because:

- it is one continuous outer substrate
- it does not invent neighboring kernel objects
- it supports interior-chip self routes naturally
- it expresses world-scale travel without introducing separate seam solvers

The main failure mode of the virtual-kernel idea is that it becomes strained for
routes like:

- `p4() -> p4()`
- `p4() -> parent`

where the row identity of the interior chip matters.

`extra` handles these more directly.

== Why This Is Better Than Kernelizing The World

Another temptation is to tessellate everything into more kernels.

That is likely a mistake for this problem because it localizes complexity in
new routing objects:

- more kernels
- more transitions
- more reconciliation

The `extra` model localizes the complexity in the routing substrate itself:

- one inner sense-aligned core
- one outer against-sense/world-scale perimeter
- explicit transfer surfaces

This is simpler than giving reverse/global routing its own solver species.

== Relationship To Overlapping Kernels

The overlapping-kernel idea remains interesting at world scale:

- `c1|c2`
- `c2|c3`
- `c3|c4`

That is a separate macro-organization question.

This document does not settle that question. What it does say is:

- even if overlapping kernels become the macro-world model
- a single kernel still seems to want:
  - an `intra` core
  - an `extra` perimeter
  - transfer geometry between them

So `extra` is compatible with either:

- current zone-based world organization
- future overlapping-kernel world organization

=== Board Expansion Requirement

The current board grid is sized exactly for `intra`. Adding `extra` regions
requires expanding the coordinate space in all four directions:

* Westward: `xwLongSpan` columns
* Eastward: `xeLongSpan` columns
* Northward: `xnLatSpan` rows
* Southward: `xsLatSpan` rows

In the expanded grid, all current intra coordinates shift by
`(xwLongSpan, xnLatSpan)`. The outer top-left corner becomes the new
`(0, 0)`.

Expanded board total size:

* Columns: `xwLongSpan + 86 + xeLongSpan` (86 = current intra col span, 19..104)
* Rows: `xnLatSpan + 48 + xsLatSpan`

This is not merely a frame placement change. It requires the board geometry
builder to know the `extra` spans before it sizes the coordinate grid, so
that `intra` is placed at the correct offset within the expanded space.
This is one of the strongest motivations for `BoardGeometrySpec` as a
first-class construction parameter — the spec must be known at grid
initialization time, not after.

For a future implementation, the vocabulary should be explicit.

Suggested families:

- `intra`
  - `wLong`
  - `nLat`
  - `eLong`
  - `sLat`
- `extra`
  - `xwLong`
  - `xnLat`

  - explicit `intra -> extra` transfer regions

== Open Questions

Several questions remain open.

=== Transfer Naming

Should transfer regions be:

- a new token family
- or an ownership rule attached to existing transition regions?

=== Corner Semantics

Should the outer perimeter corners be:

- explicit corner transfer regions

The verified geometry suggests that longitude families (`xwLong`, `xeLong`)

xnLat/xsLat row ranges). This is a tentative convention, not settled
doctrine.

== `BoardGeometrySpec` Design Doctrine

This section is doctrine only. Nothing here is implemented.

A `BoardGeometrySpec` is a first-class parameterization object passed to
the board geometry builder before grid sizing begins. It drives all
horizontal span and layout decisions. The board does not emerge from
heuristics — it is constructed from the spec.

=== Two-Phase Construction Pipeline

[source,text]
----
  chip geometry
       │
       ▼
  geometric analyzer  ──▶  minimum span constraints
                                    │
  zone config knobs  ──────────────▶┤
                                    ▼
                           BoardGeometrySpec
                                    │
                                    ▼
                           board geometry builder
                                    │
                                    ▼
                           concrete region frames
----

The geometric analyzer runs first. It reads chip geometry and derives hard
lower bounds. The spec builder takes `max(explicit, minimum)` for each span.
Explicit values can widen; they cannot squish below the analyzer minimum.

| `minWChipTerminalSpan` | chip west frame column width
| `minEChipTerminalSpan` | chip east frame column width
| `minWFanSpan`          | intra west wire count (signal + return + spacing)
| `minEFanSpan`          | intra east wire count
| `minWLongSpan`         | intra west longitude capacity
| `minELongSpan`         | intra east longitude capacity
| `latRows`              | intra signal count — nLat = sLat, always symmetric
|===

`latRows` is fully determined by signal count and is not a free parameter.

=== Derived Quantities (not free parameters)

[source,text]
----
innerCourtYardSpan  =  latLength − wLongSpan − eLongSpan
----

`innerCourtYardSpan` is a layout gap, not a named region. The lat region
spans `wLong + courtyard + eLong` columns. Both nLat and sLat share the
same column range — `latLength` is one knob, not two.

Transition zones are the overlap of lat and long regions. They are emergent
and carry no independent span term.

=== Horizontal Stack And Cascade Arithmetic

The west edge of `xwLong` is the fixed anchor. All spans accumulate
rightward. Changing any span cascades through every region to its east.

[source,text]
----
 xwLong │ wChipTerm │ wFan │ wLong │ courtyard │ eLong │ eFan │ eChipTerm │ xeLong
        ╰──────────────── latLength ───────────────────╯
----
