== Overview

This document describes the current wiring solution strategy for intra-zone routing in SignalFlow. It covers the geometric constraints, the lane assignment model, the ownership of `LONG` / `LAT` / transition regions, and the occupancy and packing doctrines used by the current board engine.

The focus is on the West-to-East (`WTE`) routing sense. North-to-South (`NTS`) is symmetric with the axes transposed, but the policy described here is only implemented for `WTE` local routing today.

== Routing Families

SignalFlow uses two routing families per zone in `WTE` sense:

=== Intra Ring (forward sense)

Carries caller→callee signals flowing West→East.

Path topology: `Wfi → Wi → Ni → Ei → Efi`

- `Wfi` / `Efi` — fan-in / fan-out regions adjacent to chip terminals
- `Wi` / `Ei` — longitude columns (vertical peel)
- `Ni` / `Si` — latitude bands (horizontal travel)
- Ni used for forward, Si for return

=== Extra Ring (reverse / recursive sense)

Carries callee→caller (backedge) and recursive signals.

Path topologies:

- `WTE_OUTER_EASTBOUND_ARC`: `Wfe → We → Ne → Ee → Efe`
- `WTE_OUTER_WESTBOUND_ARC`: `Efe → Ee → Se → We → Wfe`
- `WTE_OUTER_EASTSIGNAL_UTURN`
- `WTE_OUTER_EASTRETURN_UTURN`
- `WTE_OUTER_WESTSIGNAL_UTURN`
- `WTE_OUTER_WESTRETURN_UTURN`

The signal/return split matters. `SIGNAL` paths leave a source chip output face and enter a destination chip input face. `RETURN` paths leave a source chip input face and return to a destination chip output face. The east/west name tracks the source-side terminal band. The medial paths use the `Em` and `Wm` longitude pillars, which are 2-column-wide gaps inside the intra substrate, to enable same-side U-turns without crossing the intra ring.

== Current Routing Doctrine

The current `WTE` local routing regime is not the older "symbolic lane plus centroid rectangle" model. The live doctrine is:

- `INTRA_LONG` and `INTRA_LAT` are explicit owned travel regions
- turns may occur only inside explicit `INTRA_ROUTING_TRANSITION` regions
- occupancy is a configurable world-level doctrine: `cell` or `strip`
- lane packing is a configurable world-level doctrine: `free` or `monotone`
- independent overlap zones are the active truth surface during this phase
- full-world seam/interconnect solving is not the active target architecture

The current recommended world config for `hub.yaml`-style fan-out is:

[source,yaml]
----
world:
  sense: west_to_east
  occupancy_policy: strip
  packing_policy: monotone
----

The defaults are:

- `occupancy_policy: strip`
- `packing_policy: free`

So if a fixture wants the compact ribbon behavior, it must currently opt in to
`monotone`.

== Region Ownership

For `WTE`, the east-west ownership order must stay invariant by row, except for
truly unallocated center space. The important inner-zone reading is:

----
chip -> fan -> long -> transition -> lat -> transition -> long -> fan -> chip
----

That does **not** mean `LONG` and `LAT` overlap as peer travel regions. Instead:

- `LONG` regions carry only longitudinal travel
- `LAT` regions carry only latitudinal travel
- transition regions own the elbow where a wire changes sense

In area renders:

- `x` denotes `INTRA_ROUTING_TRANSITION`
- `X` is reserved for `INTER_ROUTING_TRANSITION`

== Lane Span

The current conservative local doctrine sizes the `WTE` `INTRA` substrate from directed same-zone wire demand, but the north and south latitude spans now count only `INTRA_PARENT_TOCHILD` demand rather than every same-zone wire indiscriminately.

For `hub.yaml` zone `(1,1)`:

- forward wires: `s1..s5`
- return wires: `r1..r5`
- total local directed-wire demand: `10`

That produces:

- west `INTRA_ROUTING_LONGITUDE`: `10` lanes
- north/south `INTRA_ROUTING_LATITUDE`: `5` lanes
- east `INTRA_ROUTING_LONGITUDE`: `10` lanes

This is intentionally conservative. `Wi` and `Ei` still track full directed same-zone demand, while `Ni` and `Si` now reflect only the forward parent-to-child bundle.

== Occupancy Doctrine

=== Cell Occupancy

Under `cell` occupancy, a route reserves only the cells it actually traverses.
Unused cells in the same lane field remain available to later wires.

This is more space-efficient but can produce uneven ribbon spacing because a
later wire may legally reuse disjoint parts of a lane family.

=== Strip Occupancy

Under `strip` occupancy, claiming a lane means claiming that lane strip in the
relevant travel family. This is more conservative, but it produces a much
clearer visual ribbon because later wires must move to the next strip rather
than opportunistically reusing partial space in the same strip.

The new engine now defaults to `strip` occupancy.

== Packing Doctrine

=== Free Packing

Under `free` packing, each wire chooses any legal lane combination permitted by
occupancy and attachment sense. This preserves correctness, but it can still
produce visually loose or gappy bundles.

=== Monotone Packing

Under `monotone` packing, `WTE` local routing is solved bundle-first rather
than route-first.

The solver:

1. chooses a contiguous window for the whole forward bundle
2. chooses a contiguous window for the whole return bundle
3. assigns each obligation a stable rank inside that window

This produces the intended ribbon behavior:

- contiguous `LAT` rows
- contiguous west/east `LONG` strips
- stable ribbon rank through the route

For `hub.yaml`, forward routing under `monotone` compacts from the old gappy
pattern:

----
free      : (47,10,53) (46,11,54) (45,12,55) (44,14,56) (43,16,57)
monotone  : (47,12,53) (46,13,54) (45,14,55) (44,15,56) (43,16,57)
----

where each tuple is:

----
(westLongCol, northLatRow, eastLongCol)
----

== Attachment Sense and Bundle Order

The new engine again carries a fine-grained attachment policy model, separate
from coarse clockwise / anticlockwise ring sense:

- `RoutingZoneChannelSense` chooses winding family
- `RoutingZoneAttachmentPolicy` chooses whether lane occupancy is claimed from
  the start or end of each relevant edge/channel family

This matters because the solver is greedy within the chosen doctrine, and lane
pick sense determines whether a bundle fans inward or outward first.

== Anchor Placement

The north/south `INTRA_LAT` bands are still placed by a search over feasible
anchors, but the objective is no longer the older blended centroid reading.

The current scorer is:

- buckle-aware
- evaluated against the actual packed lane model
- sensitive to interval overshoot, not just raw detour

This means the chosen band placement tries to reduce ugly early buckle near the
source side rather than simply minimizing a naive centroid distance.

== Current Solver Reality

The current `WTE` local solver now combines:

- explicit `LONG` / transition / `LAT` ownership
- attachment-policy-driven lane sense
- occupancy-aware legality
- optional monotone bundle compaction

What is **not** yet generalized:

- `NTS` local routing still needs the same packing treatment
- full-board overlap integration is intentionally not active until independent overlap zones are clean
- older interconnect routing remains compatibility debt, not the target solution path

== Historical Note

Older discussions of a single centroid with concentric rectangles remain useful
as intuition for why north/south bands move outward, but they are no longer a
complete description of the live solver. The new engine now has explicit travel
ownership, explicit transition ownership, configurable occupancy doctrine, and
bundle-level monotone packing.

== Chip Geometry and Port Row Position

A chip with declared terminals has this vertical structure:

----
  ┌──────────┐       ← row 0  top border
  │  func()  │       ← row 1  title
  ├──────────┤       ← row 2  separator
  ──►┤        ├──►   ← row 3  signal port   (first body row)
  ◄──┤        ├◄──   ← row 4  return port   (second body row)
  └──────────┘       ← row 5  bottom border
----

The signal port is at body row 0 (absolute row 3 from chip top).
The return port is at body row 1 (absolute row 4 from chip top).

Within the zone, a chip placed in the WEST terminal region at `orderIndex = i`
occupies world rows:

----
  slotStart  = terminalRegion.verticalStart + i * (chipHeight + 2)
  bodyStart  = slotStart + 1          ← one corridor row above chip
  signalRow  = bodyStart + 3          ← top-border + title + separator
  returnRow  = signalRow + 1
----

The `+2` slot model gives each chip one corridor row above and one below so
that the intra-zone latitude channels have symmetric room on both sides of
the chip stack — but only if those latitude channel rows are anchored relative
to the port rows rather than to the chip top/bottom borders.

== The Asymmetry Problem

The naive placement puts `INTRA_LAT/NORTH` one row above the chip's top border
and `INTRA_LAT/SOUTH` one row below the chip's bottom border.  Because the
signal port sits 3 rows down from the chip top (title bar overhead), the
effective distances are:

----
  NORTH channel → signal port : 4 rows  (3 title rows + 1 corridor)
  return port → SOUTH channel : 2 rows  (1 body row + 1 corridor)
----

This asymmetry means a route that must use the NORTH latitude channel takes a
longer detour than a route using the SOUTH channel — and for a single call pair
(root→child, child→root) where a straight horizontal line would suffice, the
solver still routes up to the NORTH channel and back down, producing unnecessary
vertical travel.

== Historical Centroid-Anchored Latitude Optimizer

=== Principle

The `INTRA_LAT/NORTH` and `INTRA_LAT/SOUTH` rows are not fixed by the chip
geometry.  They are routing resources whose optimal position depends on where
the port rows actually are.  The optimizer places them as close to the port rows
as possible and fans them outward only as far as needed to eliminate lane
collisions.

=== Port Row Centroid

When multiple chips occupy the same terminal side, their signal port rows are
spread across the chip stack.  The anchor for the latitude channels is the
**centroid** of all signal port rows on that side:

----
  centroid = mean( signalRow(chip_i) for all chips on this side )
----

Single chip: centroid = that chip's signal port row (ideal case, zero detour
for a straight route).

Multiple chips: centroid minimizes the sum of squared detours across all chips,
which is the natural optimality criterion.

=== Starting Configuration

Both latitude channels start at the centroid row:

----
  INTRA_LAT/NORTH_row = centroid
  INTRA_LAT/SOUTH_row = centroid
----

At this position, a single call pair (one forward wire, one return wire) that
enters at the signal port row and exits at the return port row can be solved as
a straight horizontal line — zero detour.

=== Collision Detection

A lane collision occurs when two route segments would occupy the same world
cell.  The solver assigns each call pair to a concentric lane `k` (k=0 is
innermost).  Lane `k` uses:

----
  north leg  : INTRA_LAT/NORTH_row - k
  south leg  : INTRA_LAT/SOUTH_row + k
  west leg   : INTRA_LONG/WEST_col - k
  east leg   : INTRA_LONG/EAST_col + k
----

Two routes on the same lane collide.  A route on lane `k` also collides with
a route on lane `k'` if their bounding rectangles share an edge segment at the
same world coordinate.

=== Optimizer Loop

----
  northRow ← centroid
  southRow ← centroid
  loop:
    assign lanes to all call pairs
    solve all routes against (northRow, southRow, westCol, eastCol)
    if no collisions: accept solution, stop
    northRow ← northRow - 1    (fan NORTH outward)
    southRow ← southRow + 1    (fan SOUTH outward)
    if northRow < zone.top or southRow > zone.bottom: error (zone too small)
----

The loop is monotone (channels only move outward) and terminates because the
zone is finite.  In practice one or two iterations suffice for typical call
trees.

=== Degenerate Cases

==== Single call pair, ports already aligned

`centroid = signalRow`.  Lane 0 has `northRow = centroid = signalRow`.  The
north leg of the concentric rectangle collapses to zero height — the route is
a straight horizontal line.  This is the intended optimal result.

==== Single call pair, signal and return on different rows

`centroid = signalRow`.  The forward route (signal row) is straight.  The
return route (return row = signalRow + 1) uses `southRow = centroid` for its
south leg — one row below the centroid, so one step of detour.  After one
optimizer step (`southRow ← southRow + 1`), the south channel moves to
`signalRow + 1 = returnRow`, giving a straight return route as well.  Zero net
detour.

==== Multiple chips, different port rows

The centroid is between the port rows.  Some chips have port rows above centroid
(their forward routes detour slightly southward to reach the centroid latitude);
others have port rows below centroid (slight northward detour).  The centroid
minimizes the total detour.  Collision detection drives the channels outward
only when actual overlaps arise.

== Historical Cases by Call Count

=== Case 1 — Single call (root → one child)

One forward wire, one return wire.  Both are straight horizontal lines at the
signal and return port rows respectively.  No concentric rectangle needed.
INTRA_LAT/NORTH and INTRA_LAT/SOUTH sit at the centroid (= signal port row);
both latitude channels are never actually entered.

----
  root:                       child:
  ┌────────┐                  ┌────────┐
  │ root() │                  │child() │
  ├────────┤                  ├────────┤
  ──►┤        ├─────────────────►┤        │
  ◄──┤        ├◄─────────────────┤        │
  └────────┘                  └────────┘
----

=== Case 2 — Two calls (root → child_a, root → child_b)

Two forward wires, two return wires.  Lane 0 handles child_a (innermost
rectangle), lane 1 handles child_b (next rectangle outward).

The centroid of {child_a signal row, child_b signal row} anchors the latitude
channels.  The optimizer fans outward until lane 0 and lane 1 do not share any
cell.

----
  root:              child_a:    child_b:
  ┌────────┐         ┌──────┐    ┌──────┐
  │ root() │         │  a() │    │  b() │
  ├────────┤         ├──────┤    ├──────┤
  ──►┤        ├──────────►┤      │    ─►┤      │
  ──►┤        ├──────────────────►┤      │
  ...return wires below...
  └────────┘         └──────┘    └──────┘
----

=== Case 3 — Self-call (loop → loop)

Source and destination are the same chip.  The route leaves the signal stub,
travels to the INTRA_LAT/NORTH channel, turns west along that channel, and
returns to the same chip's return stub — a same-side local loop.

Because source == destination, the concentric rectangle degenerates to a
U-shape on the west side only.  The NORTH latitude channel provides the
horizontal transit.

=== Case N — General

Lane assignment follows call order (call index 0 gets lane 0, call index 1
gets lane 1, etc.).  The optimizer fans the latitude channels outward until
no two lanes share a cell.  The west and east longitude columns also fan
outward in lock-step to preserve the rectangular lane shape.

== Relationship to Zone Sizing

The optimizer requires that the zone has enough vertical room above and below
the centroid to accommodate all lanes.  The zone vertical span must satisfy:

----
  totalLanes       = max call count on any one terminal side
  fansOutward      = totalLanes - 1   (lane 0 stays at centroid)
  minVertAboveCentroid = fansOutward + 1   (one row per lane + one corridor)
  minVertBelowCentroid = fansOutward + 1
----

Zone sizing (`_zoneMetrics_build`) must reserve this room.  The current
provisional formula uses `zoneVerticalSpan = 10 + chipStackHeight`; this will
be replaced by a chip-geometry-driven formula that computes the centroid and
required fan-out depth explicitly (Rule 1B).
